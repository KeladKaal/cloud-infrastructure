# Лаба 1 — Проектирование сетевой архитектуры облака (VPC, балансировщики, связность)

## 1. Цель работы

Закрепить на практике основы сетевой архитектуры облака:

- спроектировать виртуальную частную сеть (VPC) с несколькими зонами доступности;
- выбрать и спроектировать балансировщик нагрузки под конкретный сервис;
- обеспечить связность подсетей с внешним миром (IGW, NAT);
- применить чек-лист проектирования и избежать типичных ошибок;
- задокументировать получившуюся сеть.

На выходе вы получаете **проект (схему) облачной сети** для придуманного вами сервиса и **отчёт** по проекту.

> **Важно: единый формат выполнения.** Лабораторная работа выполняется как проектирование на схеме. Ресурсы в реальной облачной среде не создаются и не настраиваются, сервис не запускается. Формулировки вида «настройте», «разверните», «включите» в этой лабе означают: **спроектируйте, опишите и зафиксируйте** конфигурацию на схеме и в отчёте.

## 2. Формат выполнения

| **Параметр** | **Значение** |
| --- | --- |
| Режим работы | Индивидуально или в паре (1–2 человека) |
| Среда | Схемотехнический редактор (draw.io / Mermaid и др.); реальная облачная консоль не используется |
| Сдача | Отчёт в формате Markdown (`.md`), закоммиченный в git-репозиторий, + файл схемы |
| Запуск сервиса | Не выполняется — проектируется только сетевая топология |

## 3. Исходные данные (условие задачи)

Вы — DevOps-инженер. Специфику и название компании можно придумать самостоятельно или выбрать из списка:

- интернет-магазин;
- сервис онлайн-стриминга (видео/музыка);
- CRM-система для отдела продаж;
- банковское / финтех-приложение;
- платформа онлайн-курсов;
- SaaS-сервис для командной работы (мессенджер / таск-трекер);
- свой вариант (согласовать с преподавателем).

Заказчик просит спроектировать сетевую архитектуру для нового веб-приложения.

В отчёте (раздел 3) опишите свой сервис по шаблону:

**Название сервиса:** *укажите название*

**Тип сервиса:** *интернет-магазин / стриминг / CRM / …*

**Целевая аудитория:** *кто пользуется, из какого региона*

**Основные пользовательские сценарии:** *коротко, 2–4 сценария (например: просмотр каталога, оформление заказа, вход в личный кабинет)*

**Состав систем (сервисов):** заполните таблицу ниже — какие подсистемы нужны вашему приложению.

**Состав сервисов (заполняется под ваш проект):**

| **Сервис** | **Назначение** | **Особенности (что важно знать для проектирования)** |
| --- | --- | --- |
| *напр. веб-фронтенд* | *публичная часть сервиса* | *HTTP/HTTPS, кэширование статики* |
| *напр. API-бэкенд* | *бизнес-логика* | *REST/суммируйте пути API* |
| *напр. база данных* | *хранение данных* | *не должна быть доступна из интернета* |
| *напр. служебные сервисы* | *обновления, телеметрия* | *исходящий интернет, без входящих соединений* |

> Подставьте минимум 3–4 сервиса, характерных для вашего приложения. Пути API (например `/api/*`, `/orders/*`) и логику маршрутизации задайте под свой проект.

**Требования к отказоустойчивости:**

- Работа в **трёх зонах доступности** (AZ);
- Балансировщик: веб-фронтенд и API должны отдаваться через балансировщик нагрузки;
- Выход в интернет у всех подсетей; у приватных — **только исходящий**;
- Каждый элемент должен иметь резерв, **не должно быть Single Point of Failure**.

## 4. Задание и ход выполнения

### Этап 1. Проектирование VPC

- Задайте **CIDR-блок** для VPC. Обоснуйте выбор маски (/16 — стандарт, /20 — минимум). Убедитесь, что диапазон не пересекается ни с одной существующей сетью компании.
- Нарежьте **подсети**: в каждой из трёх зон доступности — по одной публичной, приватной и data-подсети.
- Заполните таблицу подсетей (см. шаблон в разделе «Отчёт»).
- Сформируйте **таблицы маршрутизации**:
- публичные подсети → через Internet Gateway (IGW);
- приватные подсети → через NAT Gateway;
- data-подсети → через NAT Gateway или VPC Endpoints (обоснуйте выбор).
- Нарисуйте **схему VPC** (блок-схему): три зоны, подсети, шлюзы.

**Контрольная точка 1:** не пустите БД в публичную подсеть, убедитесь, что у каждой функции есть резерв.

### Этап 2. Балансировщики нагрузки

- Определите, какие балансировщики нужны сервисам вашего проекта, и спроектируйте их конфигурацию (тип, уровень, точки размещения, правила и стратегия — на схеме и в таблице).
- Для публичных сервисов выберите тип балансировщика и опишите правила распределения: пути вашего приложения (например, `/api/*`, `/orders/*` → группа API-серверов; остальной трафик → группа фронтенда/статики).
- Обоснуйте выбор балансировщика через уровень его работы (L4 или L7).
- Для каждого балансировщика задайте параметры health check и запишите стратегию распределения (Round Robin, Least Connections и т.п.), которую выбрали и почему.
- Если для БД-репликации нужен сырой TCP — продумайте, какой балансировщик понадобился бы, и отметьте это в отчёте (в рамках проектирования).

> 💡 Подсказка: «нужно видеть HTTP-содержимое — это ALB (L7); нужны скорость и порты — это NLB (L4)».

**Контрольная точка 2:** проверьте, что маршрутизация по путям соответствует логике: API не попадает на статику и наоборот.

### Этап 3. Связность с внешним миром

- Спроектируйте **Internet Gateway** для публичных подсетей.
- Спроектируйте **NAT Gateway** для приватных и data-подсетей. Обязательно — **в каждой зоне доступности** (по одному на AZ). Обоснуйте, зачем это нужно (Single Point of Failure).
- Опишите (в тексте отчёта), как бы вы организовали запасной и основной каналы связи с on-premise-датацентром компании, если бы он существовал (Direct Connect + Site-to-Site VPN).
- Укажите, как обеспечить резервирование подключения, чтобы при падении одного канала сеть продолжала работать.

### Этап 4. Безопасность и журналирование

- Опишите, какие **Security Groups** (stateful) вы бы спроектировали для:
- веб-фронтенда;
- API-бэкенда;
- базы данных;
- NAT Gateway.
- Укажите, какие **входящие/исходящие правила** задали бы (порты, источники/назначения).
- Опишите подключение **VPC Flow Logs** и объясните, зачем они нужны и что позволяют обнаружить.

**Контрольная точка 3:** проверьте, что БД открыта только для API-бэкенда, а не для всех.

### Этап 5. Оформление отчёта

Сведите отчёт в **`.md`-файл**, поместите его в git-репозиторий и закоммитьте (см. раздел 5).

## 5. Отчёт

Отчёт оформляется как **один файл в формате Markdown** (например, `report.md`) и сдаётся через **git-репозиторий**.

### 5.1. Структура репозитория

Рекомендуемый вид репозитория:

```
название-проекта/
├── README.md            # краткое описание проекта (1–2 абзаца)
├── report.md            # основной отчёт по разделам ниже
├── scheme/              # файлы схем (PNG/SVG/JPEG)
│   └── vpc.png
└── (доп. файлы по необходимости)
```

> `README.md` — короткое вступление; подробности размещайте в `report.md`.

Этот репозиторий заводится один раз и дальше используется во всех лабораторных курса — каждая следующая лаба добавляет в него свою папку и свой раздел.

### 5.2. Содержание `.md`-отчёта

Файл `report.md` должен включать следующие разделы (оформляются как `##`-заголовки Markdown):

- **## 1. Обоснование CIDR** — выбранный диапазон и маска, объяснение, почему он не пересекается с другими сетями.
- **## 2. Таблица подсетей** — оформленная Markdown-таблицей (см. шаблон ниже).
- **## 3. Схема сети** — вставка изображения схемы (или ссылка на файл в `scheme/`).
- **## 4. Балансировщики** — таблица с типами, уровнями и правилами.
- **## 5. Связность и резервирование** — описание IGW, NAT, каналов и резервирования.
- **## 6. Безопасность** — Security Groups и VPC Flow Logs.
- **## 7. Выводы** — что запомнили, каких ошибок избежали, что нового узнали.

### 5.3. Обязательные таблицы

**Таблица подсетей:**

| **Зона** | **Подсеть** | **CIDR** | **Тип** | **Маршрут по умолчанию** |
| --- | --- | --- | --- | --- |
| AZ1 | публичная | 10.0.1.0/24 | public | IGW |
| AZ1 | приватная | 10.0.10.0/24 | private | NAT GW |
| AZ1 | data | 10.0.20.0/24 | data | NAT GW / Endpoint |
| AZ2 | ... | ... | ... | ... |
| AZ3 | ... | ... | ... | ... |

**Таблица балансировщиков:**

| **Сервис** | **Тип балансировщика** | **Уровень** | **Правило / стратегия** |
| --- | --- | --- | --- |
| *фронтенд вашего проекта* | ALB | L7 | `/api/*`, `/orders/*` → API; остальное → фронтенд |

*(подставьте сервисы и пути вашего проекта).*

### 5.4. Сдача через git (шаги)

Инициализируйте репозиторий и добавьте файлы:

```bash
git init
git add README.md report.md scheme/
```

Создайте первый коммит:

```bash
git commit -m "Лаба 1: сетевая архитектура облака"
```

Если репозиторий удалённый (например, на GitHub / GitLab / внутреннем сервере):

```bash
git remote add origin <URL-репозитория>
git push -u origin main
```

Пришлите преподавателю ссылку на репозиторий или архив с коммитами.

> Если сдаёте в паре — оба участника должны быть соавторами коммитов (см. 5.5).

### 5.5. Работа в паре

- Создайте общий репозиторий и ведите работу через ветки/коммиты двумя аккаунтами.
- В `README.md` укажите обоих авторов.

## 6. Чек-лист самопроверки (перед сдачей)

Пройдитесь по списку и поставьте «галочку» напротив каждого пункта:

- ☐ Сервис описан: название, тип, аудитория, сценарии, состав систем.
- ☐ CIDR-блок: маска /16 или меньше, без пересечений с существующими сетями.
- ☐ Подсети: минимум по одной в каждой из трёх зон доступности (публичная + приватная + data).
- ☐ Маршрутизация: публичные → IGW, приватные → NAT/Endpoints.
- ☐ Балансировщик выбран корректно по уровню (L4/L7) — обосновано в отчёте.
- ☐ Health checks описаны для всех групп серверов.
- ☐ NAT Gateway — в каждой зоне доступности (нет SPOF).
- ☐ БД не в публичной подсети, доступна только API-бэкенду.
- ☐ Подключение VPC Flow Logs описано.
- ☐ Резервирование каналов описано (Direct Connect + Site-to-Site VPN).
- ☐ Схема сети и документация маршрутов приложены.
- ☐ Спроектированная конфигурация зафиксирована на схеме и в таблицах отчёта (реальные ресурсы в облаке не создавались).

## 7. Контрольные вопросы (по итогам работы)

Отвечают устно на защите или письменно в конце отчёта.

- Чем VxLAN отличается от VLAN? Какие ограничения VLAN решает VxLAN?
- ALB или NLB для gRPC и WebSocket? Аргументируйте через уровень работы балансировщика.
- Что будет с CDN, если не выставить Cache-Control? Почему важно настроить TTL для API?
- Сколько NAT Gateway нужно в production на 3 зоны доступности и почему?
- Чем Security Group отличается от Network ACL (stateful vs stateless)?
- Почему нельзя держать базу данных в публичной подсети?
- Зачем нужны VPC Flow Logs и что они позволяют обнаружить?
