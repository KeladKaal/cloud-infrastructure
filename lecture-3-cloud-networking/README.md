## Часть 1. Виртуализация сетей (15 минут)

### Проблема физических сетей

Представьте себе классическую сеть в 2010-м. У вас есть стойки, коммутаторы, кабели, и вы физически протягиваете сеть между серверами. Хотите добавить новую изолированную сеть? Идёте коммутировать кабели заново, переписываете VLAN-теги на коммутаторах. Это медленно, хрупко и недешёво.

А теперь представьте облако, где один провайдер создаёт **миллионы изолированных сетей для разных клиентов** — одновременно, мгновенно и без единого движения кабеля. Физический подход тут физически невозможен.

Поэтому облаком управляет **SDN — Software-Defined Networking, программно-определяемые сети**. Ключевая идея SDN: мы отделяем **управляющую плоскость** (где всё решается, контролируется централизованно) от **плоскости данных** (где пакеты реально летят по железу):

### VLAN — первый шаг

Самый старый инструмент виртуализации на уровне L2 — **VLAN**, стандарт IEEE 802.1Q. Идея простая: один физический коммутатор мы логически режем на несколько независимых сетей, помечая кадры тегом. Тег VLAN занимает 12 бит, поэтому таких сетей максимум **4094**.

VLAN изолирует broadcast-домены, это удобно. Но для облака VLAN не подходит — и вот почему:

- **4094 сетей — мало.** У провайдера клиентов больше.
- Всё завязано на один **L2-домен** и на протокол **Spanning Tree**, который блокирует избыточные пути и замедляет сеть.

![](images/l3-image3.png)

То есть VLAN — это хороший внутренний инструмент провайдера для физической сегментации стоек, но не решение для мультитенатности облака. Переходим к следующему уровню.

**Вопрос аудитории:** как думаете, когда 4094 сетей — это много, а когда — катастрофически мало?

### VPC — Virtual Private Cloud

Следующая ступень — **VPC, Virtual Private Cloud**. Это уже логически изолированная частная сеть в пределах облака, которую заводит клиент. По сути, каждый клиент получает свой мини-датацентр, где сам управляет адресацией, маршрутизацией и правами доступа.

Важное отличие от VLAN: VPC работает на **Layer 3** — на уровне IP-адресов и маршрутов, а не на уровне кадров Ethernet. И она может растягиваться на несколько зон доступности.

- **CIDR-блок** — диапазон IP, например 10.0.0.0/16. Это «адресное пространство» вашей сети.
- **Подсети (subnets)** — вы нарезаете CIDR на куски и кладёте их в разные зоны доступности (AZ), чтобы получить отказоустойчивость.
- **Таблица маршрутизации** — определяет, куда пакет уходит дальше.
- **Интернет-шлюз (IGW)** — обеспечивает двусторонний доступ в интернет.
- **NAT-шлюз** — только исходящий доступ для приватных подсетей.
- **Security Groups и Network ACL** — фильтрация трафика.
- **VPC Flow Logs** — журналирование трафика для аудита.

### VxLAN — как облако решает главную проблему

И вот он, ключевой игрок — **VxLAN**, протокол из стандарта RFC 7348. Это туннельный протокол: он **инкапсулирует целый Ethernet-кадр внутрь UDP-пакета** на порту 4789 и отправляет его через IP-сеть. Внутри ставится 24-битный идентификатор сети — **VNI**. А 24 бита — это **до 16 миллионов виртуальных сетей**. Сравните с 4094 у VLAN.

Как это работает: физическая сеть — это **underlay** (базовая транспортная среда на IP), а поверх неё строится **overlay** — виртуальные L2-сети клиентов. На границе работают устройства **VTEP** — они и делают инкапсуляцию и деинкапсуляцию кадров:

![](images/l3-image5.png)

Зачем Всё это в облаке:

- **Нативная мультитенатность** — миллионы клиентов, каждый в своей виртуальной сети.
- Не нужен Spanning Tree, потому что L2 теперь живёт поверх IP, а значит, можно строить топологию **Spine-Leaf** без блокировок.
- Можно расширять L2-домен через всю IP-фабрику.

| **Технология** | **Уровень** | **Макс. сетей** | **Использование** |
| --- | --- | --- | --- |
| **VLAN** | L2 | 4094 | Малые сети, сегментация стоек |
| **VPC** | L3 | до миллионов | Сеть клиента в облаке |
| **VxLAN** | L2 over L3 | 16 млн (VNI 24 бит) | Мультитенатность облака |

**Итог по части 1:** VLAN — для небольших сетей, VPC — для клиента облака, VxLAN — технология, которая делает облако возможным. Запомните эту тройку.

## Часть 2. Балансировщики нагрузки (15 минут)

Сеть у нас есть. Теперь возникает вопрос: как распределить огромный трафик между множеством одинаковых серверов? На помощь приходят балансировщики нагрузки. Их два главных типа — и они работают на разных уровнях.

### ALB — Application Load Balancer

**ALB работает на Layer 7** — на уровне приложения, то есть понимает не только IP и порты, но и содержимое запроса: путь, заголовки, хост, тело.

Что он умеет:

- **Content-based routing** — распределение по содержимому запроса.
- **Path-based routing**: например, всё, что идёт на /api/*, — в одну группу серверов, а /static/* — в другую.
- **Host-based routing**: app1.example.com на один кластер, app2.example.com — на другой.
- **SSL/TLS termination** — снимает шифрование, разгружая бэкенд.
- Работает с WebSocket, HTTP/2, HTTP/3, gRPC.

![](images/l3-image6.png)

<summary>Исходник диаграммы (Mermaid)</summary>


Пример правила, которое вы будете настраивать на практике:

IF host = api.myshop.com AND path = /orders/*

THEN forward to target-group 1

Когда выбирать ALB? Веб-приложения, API-шлюзы, микросервисы с разными endpoints. Запомните: задержка ALB — порядка единиц миллисекунд, это нормально.

### NLB — Network Load Balancer

**NLB работает на Layer 4** — на уровне TCP/UDP. Он не смотрит на содержимое, ему хватает IP-адресов и портов.

Сильные стороны NLB:

- Гигантская производительность — **до миллионов запросов в секунду**.
- Минимальная задержка — порядка **100 микросекунд**.
- **Сохраняет исходный IP клиента** — важно для whitelist и логирования.
- Может иметь **статический Elastic IP** — фиксированный адрес, который не меняется.

![](images/l3-image7.png)

<details>
<summary>Исходник диаграммы (Mermaid)</summary>

```mermaid
flowchart LR
U[Клиент] --> NLB[NLB · Layer 4<br/>TCP/UDP]<-->|"пакет на IP:порт"| S1[(Сервер 1)]

NLB <-->|"пакет на IP:порт"| S3[(Сервер 3)]
```

</details>

Когда выбирать NLB? Для TCP/UDP-протоколов, gRPC, WebSocket, игровых серверов, raw TCP (MySQL-репликация). Нужен фиксированный IP для белых списков — это NLB.

**Быстрый опрос:** gRPC — к какому балансировщику понесём? (пауза) Правильно, к NLB на L4. А веб-приложение с путями — к ALB. Запомните правило: нужно **«видеть» HTTP-содержимое — берите ALB, нужна скорость и порты — берите NLB.**

#### Сравнение ALB и NLB

| **Характеристика** | **ALB** | **NLB** |
| --- | --- | --- |
| Уровень | Layer 7 (приложение) | Layer 4 (транспорт) |
| Производительность | до сотен тыс. rps | до миллионов rps |
| Задержка | единицы мс | ~100 мкс |
| Понимает HTTP/URL/хост | да | нет |
| Сохраняет IP клиента | нет (по умолч.) | да |
| Статический Elastic IP | нет | да |

### Стратегии распределения

Какой бы балансировщик вы ни взяли, ему нужна стратегия отправки запросов:

![](images/l3-image8.png)

<details>
<summary>Исходник диаграммы (Mermaid)</summary>

```mermaid
flowchart LR
LB[Балансировщик]
LB -->|"Round Robin · по кругу"| R1[Сервер]
LB -->|"Least Connections · мин. соединений"| R2[Сервер]
LB -->|"Weighted · по весам"| R3[Сервер]
LB -->|"IP Hash · привязка клиента"| R4[Сервер]
```

</details>

- **Round Robin** — по кругу, просто и без учёта нагрузки.
- **Least Connections** — на сервер с наименьшим числом активных соединений.
- **Least Outstanding Requests** — на сервер с наименьшей очередью (актуально для HTTP/2).
- **Weighted** — с весами, когда сервера разной мощности.
- **IP Hash** — привязка клиента к серверу по хэшу его IP (для липких сессий).

На практике чаще всего используют **Least Connections в сочетании с весами**.

## Часть 3. DNS, CDN, Anycast, Socket Saving (12 минут)

Теперь поднимемся на глобальный уровень. Сеть мы построили, трафик распределили, — но как пользователь из другого континента вообще попадает к нам, и почему сайт грузится быстро?

### Продвинутый облачный DNS

DNS — это телефонная книга интернета, но облачный DNS умеет гораздо больше простого «домен → IP»:

- **Latency-based routing** — отдаём IP ближайшего по задержке кластера.
- **Geolocation routing** — по стране или региону. Например, пользователь из ЕС получает наш сервер в ЕС, чтобы соблюдать GDPR.
- **Weighted routing** — для A/B-тестирования: например, 5% трафика на новую версию сервиса.
- **Failover routing** — если основной сервер недоступен, DNS автоматически отдаёт резервный IP.
- Интеграция с **health checks** — DNS не отдаёт IP мёртвого сервера.

### CDN — Content Delivery Network

Зачем нужен CDN? Проблема в том, что задержка растёт с расстоянием. Если сервер в Москве, а пользователь во Владивостоке, каждый запрос идёт тысячи километров.

CDN решает это **географическим кэшированием**. DNS отдаёт пользователю ближайший **edge-сервер** (точку присутствия, PoP). Edge проверяет свой кэш:

![](images/l3-image9.png)

<details>
<summary>Исходник диаграммы (Mermaid)</summary>

```mermaid
flowchart TB
User[Пользователь]<-->|"request (hit)"| E[Edge-сервер CDN<br/>ближайший PoP]
```

- Если контент есть и не истёк — **отдаёт сразу, быстро (hit)**.
- Если кэша нет (**miss**) — идёт к **origin**-серверу, забирает и кэширует.

Тонкость с **TTL**: у разных типов контента разное время жизни в кэше. Статика и видео кэшируются долго, а API — очень коротко, иначе пользователи будут получать устаревшие данные. Управляется это заголовком Cache-Control.

Провайдеры, которые вы встретите: CloudFront, Cloudflare, Akamai, G-Core, Yandex CDN.

### Anycast-сети

Ещё один мощный инструмент — **Anycast**. Идея: множество серверов по всему миру объявляют через BGP **один и тот же IP-адрес**. Маршрутизаторы направляют пакет к **топологически ближайшему** серверу.

Сравним с обычным unicast: там один IP = один сервер. В anycast один IP = десятки серверов, и каждый пользователь попадает к ближайшему.

Где это работает:

- **DNS** (вспомните 1.1.1.1 от Cloudflare),
- **edge-серверы CDN**,
- **API-шлюзы**,
- **защита от DDoS** — атака распределяется по всем точкам присутствия, и ни одна не перегружается.

### Socket Saving

Последняя тема блока — сбережение сокетов. Звучит загадочно, но важно. Каждое TCP-соединение занимает на сервере память и дескрипторы. При миллионах пользователей число одновременных соединений растёт линейно, и сервер задыхается.

![](images/l3-image11.png)

<details>
<summary>Исходник диаграммы (Mermaid)</summary>

```mermaid
flowchart LR
subgraph Obychno [Без сбережения · 1 запрос = 1 соединение]
M1[Соединение 1] --> S[(Сервер)]
M2[Соединение 2] --> S
M3[Соединение 3] --> S
end
subgraph Sberezhenie [Socket Saving · мультиплексирование]
O1[[Одно TCP-соединение]]
O1 --> S2[(Сервер)]
end
```

</details>

Как с этим бороться:

- **Connection Multiplexing** — одно TCP-соединение обслуживает много параллельных запросов. Это делают HTTP/2, HTTP/3, gRPC.
- **Keep-Alive на балансировщике** — соединение не закрывается, а возвращается в пул и переиспользуется.
- **Connection Pooling на приложении** — например, pgbouncer для баз данных, чтобы не плодить новые соединения на каждый запрос.

**Итог блока:** DNS направляет, CDN кэширует, Anycast ускоряет и защищает, а Socket Saving не даёт серверу захлебнуться соединениями.

## Часть 4. Пограничные шлюзы, NAT, VPN (10 минут)

Сеть построена, трафик распределён, контент кэшируется. Теперь важный момент — как облачная сеть связана с внешним миром: с интернетом и с on-premise инфраструктурой компании.

```mermaid
IGW <--> Internet[Интернет]
NAT --> Internet
```

</details>

- **IGW, Internet Gateway** — **двусторонний** доступ: и входящий, и исходящий. Его цепляют к публичным подсетям. IGW горизонтально масштабируется и не создаёт узких мест.
- **NAT Gateway** — **только исходящий** доступ для приватных подсетей. Внутренние сервера могут ходить в интернет (обновляться, качать образы), но из интернета к ним попасть нельзя.

Почему это важно: NAT **не принимает входящие соединения**. Это защита приватных сервера — их никто не «видит» из интернета.

**Критический совет:** в production ставьте **NAT Gateway в каждую зону доступности**. Если поставить один NAT в одной AZ — и эта AZ упадёт, весь исходящий трафик встанет. Это Single Point of Failure, мы к нему вернёмся в ошибках.

Есть и дешёвая альтернатива — **NAT Instance** (обычная виртуальная машина с настроенной трансляцией адресов). Но за него надо вручную обновлять и настраивать HA — как правило, это не стоит выгоды.

### VPN-подключения

Второй способ связи с внешним миром — VPN. Тут два сценария:

- **Site-to-Site VPN** — связывает on-premise датацентр компании с облачной VPC. Работает по протоколу IPsec (IKEv1/IKEv2), с шифрованием AES-256 и SHA-256. Правильный вариант резервирования — создавать **два туннеля, по одному в каждую зону доступности**. Также обычно включают Perfect Forward Secrecy — чтобы компрометация одного ключа не вскрыла всю переписку.
- **Client VPN** — для удалённых сотрудников. Это OpenVPN или готовые решения вроде AWS Client VPN.

### Direct Connect / ExpressRoute

А если нужно больше, чем VPN? Если нужна **стабильная задержка и гигабитные скорости** — есть выделенное физическое волокно, **Direct Connect** (в Azure — ExpressRoute). Оно не идёт через публичный интернет, скорость — сотни гигабит. Но это дорого, а настройку согласуют неделями.

### Transit Gateway — центральный хаб

И последнее в этом блоке. Когда у компании много VPC, если связывать их попарно пирингами, получится «паутина» из сотен соединений — неразбериха. Решение — **Transit Gateway**, единый центральный узел-концентратор.

![](images/l3-image15.png)

<details>
<summary>Исходник диаграммы (Mermaid)</summary>

Он поддерживает до **5000 подключений VPC**, умеет **inter-region peering** (связать регион Москвы и Стамбула), и главное — **централизует сетевые политики и firewall**. Всё управление маршрутами — в одном месте, через route tables.

**Итог блока:** IGW и NAT — выход в интернет, VPN и Direct Connect — связь с on-premise, Transit Gateway — централизация сети.

## Часть 5. Практика и резюме (8 минут)

И финальный блок — как применить всё это на практике и не наступить на грабли.

### Чек-лист проектирования сети

Когда проектируете сеть под production, пройдитесь по этому списку:

![](images/l3-image16.png)

<details>
<summary>Исходник диаграммы (Mermaid)</summary>

```mermaid
flowchart TD
A[1. CIDR-блок · /16, без пересечений] --> B[2. Подсети · мин. 3 AZ<br/>публичная + приватная + data]
B --> C[3. Маршрутизация · публичные → IGW<br/>приватные → NAT / VPC Endpoints]
C --> D[4. Безопасность · SG + NACL + Flow Logs]
D --> E[5. Документация · схема сети, таблицы портов]
```

</details>

- **CIDR-блок**: берите /16 — стандарт, /20 — минимум. И обязательно проверьте, что он не пересекается с существующими сетями компании, — иначе маршруты «съедят» друг друга.
- **Подсети**: минимум три зоны доступности, и в каждой — публичная подсеть /24, приватная /24 и data /24.
- **Маршрутизация**: публичные подсети → IGW; приватные → NAT Gateway или VPC Endpoints.
- **Безопасность**: Security Groups (stateful-фильтрация), NACL (stateless), и обязательно включите VPC Flow Logs.
- **Документация**: нарисуйте схему сети, сведите таблицы маршрутизации и список открытых портов. Без документации через месяц вы сами не вспомните, почему в маршруте так.

### Типичные ошибки

Теперь — классика, на которой ломаются новички:

| **#** | **Ошибка** | **Последствие** |
| --- | --- | --- |
| 1 | Слишком большой CIDR, например /8 | Раздут маршрут, сложно нарезать подсети |
| 2 | Одна подсеть на все зоны | Нет отказоустойчивости и резерва |
| 3 | Один NAT Gateway в одной AZ | Упадёт зона — встанет весь исходящий трафик |
| 4 | Нет VPC Flow Logs | «Слепые» — не видно, кто/куда ходит |
| 5 | **БД в публичной подсети** | База видна из интернета → компрометация |

- **Слишком большой CIDR**, например /8. Не надо. /16 достаточно почти всегда.
- **Одна подсеть на все зоны доступности.** Это убивает отказоустойчивость — нет резерва.
- **Один NAT Gateway в одной зоне.** Упадёт зона — встанет весь исходящий трафик.
- **Нет VPC Flow Logs.** Вы «слепые» — не видите, кто и куда ходит в вашей сети.
- И самое опасное — **БД в публичной подсети.** База видна из интернета. Это прямой путь к компрометации.

### Итоги лекции

Давайте соберём главное. Мы выяснили, что облако держится на виртуализации сетей: VLAN — для небольших сетей, VPC — для клиента, VxLAN — технология мультитенатности. Трафик распределяют ALB (уровень приложения) и NLB (уровень сети). Глобально нас ускоряют DNS-маршрутизация, CDN-кэш и Anycast, а не дают захлебнуться — Socket Saving. Связь с миром строят IGW, NAT, VPN, Direct Connect и Transit Gateway.

**Ключевая мысль сегодня:** хорошая сетевая архитектура — это когда каждая функция имеет резерв, у каждого запроса есть понятный путь, а у вас есть журналы и документация.
